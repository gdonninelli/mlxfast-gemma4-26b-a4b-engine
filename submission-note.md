# Gemma 4 26B A4B MLX.fast optimization submission

## Goal

The goal of this submission was to improve the Gemma 4 26B A4B MLX inference engine for the Yukon MLX.fast challenge, with particular focus on the Mixture-of-Experts prefill path.

The main constraint was to improve execution efficiency without changing model semantics or the frozen target weights. I therefore focused on kernel fusion, routing overhead, memory reuse, and specialized execution paths rather than changing quantization or model structure.

The score is dominated more heavily by decode than prefill, but this branch primarily explored prefill-side MoE optimizations while preserving the existing decode path.

## Environment and setup

Development was performed on Apple Silicon using the Swift MLX engine provided by the challenge repository.

The main modified file was:

Vendor/mlx-swift-lm/Libraries/MLXLMCommon/SwitchLayers.swift

The runtime worker was built using:

swift build -c release --force-resolved-versions

The benchmark was executed using:

MLXFAST_ENGINE_BIN=.build/release/mlxfast-runtime-worker \
MLXFAST_CORRECTNESS_GOLDEN_PATH=correctness_prompts/public_longcopy_gate_english_1024_1024.json \
./benchmark.sh --local-iterate

For individual runs I also used MLXFAST_SCORE_PATH to preserve benchmark results.

The official-runner constants printed by the local benchmark harness were approximately:

0.0003276219582519531 seconds/token

decode baseline:
0.012374741210937498 seconds/token

These constants were used by the harness when calculating the local estimated score.

## Starting point and prior work

The branch was based on the upstream challenge implementation and already contained several optimized paths.

Relevant existing mechanisms included:

- counting-sort based MoE routing
- PREFILL-CSORT routing
- PromptGlue2 routing scan
- fused/shaped GeGLU support
- specialized Gate/Up execution
- quantized SwitchLinear projections
- weighted expert unsort/reduction
- NAX-based matrix kernels already present elsewhere in the engine

The branch initially contained an earlier fused NAX MoE prefill experiment.

During rebasing onto a newer upstream version, a conflict appeared in SwitchLayers.swift because upstream had introduced a PromptGlue2 route scan while the local optimization expected additional metadata for the NAX path.

Instead of selecting either side of the conflict, I combined them.

The PromptGlue2 scan was extended so that the routing pass could retain and emit:

- block offsets
- expert offsets
- tile offsets

This allowed the newer routing path to remain in use while still exposing metadata required by the experimental specialized kernels.

For the 128-expert Gemma configuration, the PromptGlue2 scan uses a decomposition based on routing blocks and expert columns and writes terminal expert prefix information required by subsequent execution stages.

## Optimization hypothesis

The main performance hypothesis was that the MoE projections could benefit from more aggressive specialization for the actual Gemma workload.

Each selected expert contains Gate, Up, and Down projections.

For the relevant Gemma MoE dimensions, the Down projection consumes an activation of width 704 and produces width 2816.

The idea was to experiment with a specialized NAX-based down-projection kernel that processes a small logical group of routed rows together.

The intended benefits were:

1. reduce generic kernel overhead
2. specialize the matrix shape for the exact Gemma expert dimensions
3. reuse routing metadata already generated by PREFILL-CSORT
4. avoid unnecessary intermediate transformations
5. potentially exploit threadgroup-local reuse of activations
6. reduce launch and dispatch overhead by executing a more specific kernel

## NAX down-prefill experiment

I added an experimental NAX down-projection prefill path.

The experiment is controlled by:

DARKBLOOM_GEMMA4_PREFILL_NAX_DOWN

It defaults to OFF.

The specialized kernel was named:

gemma4_prefill_nax_down_m8_v1

The implementation reused the existing NAX infrastructure and the existing flash_moe_qmm_t_nax implementation rather than adding an entirely unrelated matrix kernel.

The intended logical tile configuration was:

logical M = 8 rows

physical NAX BM = 16 rows

BN = 64

BK = 64

64 threads

2 SIMD groups

The physical matrix fragment requires 16 rows, while only up to 8 logical routed rows are active for this experiment.

For the Gemma Down projection:

K = 704

N = 2816

This gives:

11 K steps of size 64

44 N tiles of size 64

The implementation used the existing quantized expert weights.

The Down projection fast path was restricted to the expected Gemma shape and data types.

The path checks conditions including:

- bf16 activation
- sufficiently large prefill row count
- flattened uint32 routing indices
- Gemma expert count
- expected 704 to 2816 Down projection dimensions
- supported quantized SwitchLinear layout
- no unsupported bias configuration

The relevant quantized weight representation observed in the implementation was approximately:

weights:
[128, 2816, 88] uint32

scales/bias metadata:
[128, 2816, 11] bf16

The implementation used expert offsets and tile offsets produced by PREFILL-CSORT.

Two call sites were added before the normal Down projection path so that the specialized implementation could be selected when all conditions were satisfied.

## Important tradeoff discovered

The NAX down-projection experiment exposed an important weakness in the initial design.

The small logical M=8 tile improves specialization, but it also reduces reuse of each expert's Down weights compared with a larger row tile.

The incumbent implementation can amortize weight traffic over significantly more routed rows.

With M=8, the same expert weights may be loaded much more frequently.

This means that even if arithmetic and dispatch are efficient, memory traffic can dominate.

Additionally, the first implementation serialized all 44 N tiles within the same work structure rather than spreading the N dimension more aggressively across the grid.

This reduced available parallelism.

Before benchmarking, this suggested that the design might be slower than the incumbent path despite being more specialized.

A possible follow-up would be to include the N tile in the dispatch grid and increase parallelism while preserving expert/row routing metadata.

## Failure observed

The experimental NAX Down path was benchmarked with:

DARKBLOOM_GEMMA4_PREFILL_NAX_DOWN=1

The worker failed with a Metal GPU watchdog timeout.

The relevant failure was:

Command buffer execution failed:
Caused GPU Timeout Error
kIOGPUCommandBufferCallbackErrorTimeout

The worker terminated with signal 6.

No valid score was produced for this configuration.

This was an important negative result.

Rather than enabling an unstable fast path, the optimization remains disabled by default.

The submission therefore preserves the code for experimentation but does not activate this path in the normal benchmark environment.

## Course correction

After the GPU timeout, I did not continue trying to force the NAX Down path into the default execution.

Instead, the default path was kept unchanged for this experiment:

DARKBLOOM_GEMMA4_PREFILL_NAX_DOWN defaults to OFF.

This means the failed experimental kernel should not execute unless explicitly enabled.

The branch therefore retains the routing integration and other fused MoE work while avoiding the known GPU-timeout configuration.

This was preferable to enabling an optimization with uncertain correctness or runtime stability.

## Current branch contents

The main areas affected by this work are:

1. PromptGlue2 routing integration

The routing scan was extended so that it can provide the expert and tile prefix metadata needed by specialized execution paths while retaining the newer upstream routing implementation.

2. Fused MoE prefill work

The branch contains specialized MoE prefill experiments intended to reduce redundant routing and projection overhead.

3. Gate/Up prefill fusion

The implementation retains the specialized Gate/Up execution path used for prefill.

4. NAX Down-prefill experiment

A specialized Down projection kernel was added for experimentation but remains disabled by default because the initial configuration triggered a GPU watchdog timeout.

## Lessons learned

The most important result from this iteration was that simply creating a smaller and more specialized matrix kernel is not automatically beneficial for MoE.

For expert projections, reuse of expert weights across routed rows is crucial.

A logical M=8 configuration can substantially increase repeated weight traffic compared with a larger tile.

For the 704 to 2816 Down projection, this effect is especially important because each output tile requires significant expert weight bandwidth.

The experiment also showed that serializing the full N dimension inside a small work unit can create long-running GPU work and insufficient parallelism.

The GPU timeout reinforces the need to design the dispatch topology together with the matrix tile shape rather than considering the matrix microkernel alone.

The routing metadata work remains useful because expert offsets and tile offsets can support other specialized execution strategies without repeating routing work.

## Caveats

Local scores vary considerably between runs.

The benchmark is sensitive to system state, temperature, and other execution conditions.

For this reason, the claimed score is only a local estimate.

The official Yukon runner should provide the meaningful comparison because candidate and baseline are measured under controlled conditions.

The NAX Down path should not be interpreted as a completed optimization.

It is intentionally disabled by default.

## Next steps

The most promising continuation would be to redesign the specialized Down projection around a better work decomposition.

Possible directions include:

- grid over both routed row tile and N tile
- increase expert-weight reuse before reducing M
- avoid serial execution of all 44 N tiles in one work unit
- measure Down projection independently before integrating it into the full MoE pipeline
- reuse existing PREFILL-CSORT metadata without adding additional routing passes
- focus future work on optimizations that also improve decode, since decode carries greater weight in the benchmark score
- reduce launch and routing overhead only when measurement shows that it is a meaningful fraction of total runtime

The current submission is therefore a stable checkpoint containing the routing/fusion work and a disabled experimental kernel, with default correctness passing and a local claimed score of approximately 0.464.
